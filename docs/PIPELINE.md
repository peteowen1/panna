# panna pipeline

_Generated by `ops/scripts/pipeline_guide.py` from `docs/pipeline.json`, using runs up to 25 Nov 2026, 3:01am (Sydney time). Do not edit by hand, except the notes section: rerun the generator._

How the football ratings and match predictions get built on GitHub Actions: four workflows. Three are started by the daily Opta scrape in the pannadata repo: the Predictions Pipeline builds the match predictions and the blog's game logs and publishes them; the Opta RAPM/SPM Pipeline refits the player ratings and publishes them; the EPV/WPA Model Training workflow scores shots and passes and publishes the xMetrics files. The Skills Seasonal Build runs weekly on its own and publishes the skill ratings tables. The pannadata repo's pipeline guide covers the scrape before these and the blog data build after them. Each workflow is timed on its own; runs are not stitched across repos.

## Skills Seasonal Build

Workflow: [`skills-seasonal.yml`](https://github.com/peteowen1/panna/blob/HEAD/.github/workflows/skills-seasonal.yml). Median wall time **43 min 21 s** (range 39 min 43 s to 1 h 08 min), from the first job starting to the last job ending, over the 3 run(s) listed below.

Rebuilds the player skills chain on a runner (it used to be run by hand): match stats, the recency-weighted RAPM target, skill features, the skill SPM and the seasonal skill ratings, then checks the new tables against the published ones and publishes them to the predictions-cache release (which the Predictions Pipeline downloads as required input). Each stage is its own job on a fresh machine, passing files on as run artifacts. Counted: weekly scheduled runs on main (only three exist so far, so fewer than 5 runs back this guide).

**What starts it, and what it starts:** GitHub's own schedule, set for Monday 3pm Sydney time in summer (2pm in winter); it can also be started by hand. It starts nothing itself: the Predictions Pipeline reads the 06_seasonal_ratings.rds and psr_league_offsets.parquet it publishes.

## How to regenerate

```
python C:/dev/ops/scripts/pipeline_guide.py build --repo-dir <this repo>
```

It reads `docs/pipeline.json` (which workflows and jobs are the pipeline, one line per step) and the latest successful runs through `gh`, saves every response raw, and rewrites this file and `docs/pipeline-summary.json`. It fails if the config names a job, step or log pattern that no longer appears, so a renamed step cannot leave a stale description behind. Steps marked **(not confirmed)** were not checked against the script they run.
